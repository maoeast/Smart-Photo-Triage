## Failure meaning

Twenty parameterized behavioral cases reach the Phase G public capability boundary and prove that
the pre-implementation repository has no executor/recovery module. One separate parser assertion
proves that none of the required `apply`, `doctor`, `resume`, or `rollback` CLI routes exists.

The 21 cases specify observable contracts for:

- T-G-001 dry-run with no source, target, output-root, transaction, or journal mutation;
- T-G-002/T-G-003 no-overwrite and unowned `ALREADY_PRESENT` handling;
- T-G-004 through T-G-011 durable COPY/MOVE boundary states and deterministic resume after
  `AFTER_PREPARED`, `AFTER_PARTIAL_COPY`, `AFTER_TARGET_VERIFY`, `AFTER_FINALIZE`,
  `BEFORE_SOURCE_DELETE`, `AFTER_SOURCE_DELETE`, and `BEFORE_DONE`;
- T-G-012 bundle partial failure that cannot become bundle/transaction `DONE` until resume;
- T-G-013/T-G-014 exclusive mutation locking with live, unknown, and proven-dead owner rules;
- T-G-015 repeated-plan idempotency without target-name drift;
- T-G-016 through T-G-019 safe copy/move rollback, output containment, modified-target refusal,
  and rerun idempotency;
- T-G-020 recoverable permission failure without false `DONE`;
- exact payload/revision approval revalidation while the mutation lock is held;
- rejection of a target-parent reparse point introduced after read-only preflight;
- required CLI route registration.

The RED is meaningful because the assertions are filesystem, SQLite journal, fault-boundary,
locking, approval, recovery, and rollback outcomes. The test file contains no syntax error,
intentionally false assertion, network call, real photo path, or implementation mock that bypasses
real temporary-file I/O.

## Review-remediation REDs

After the first focused GREEN, two recovery gaps were converted into behavioral tests before their
remediation:

```text
rtk python -m pytest -q tests/test_phase_g_executor.py -k "second_transaction or copied_verified_commit_crash"
FF                                                                       [100%]
2 failed, 31 deselected in 0.80s
```

The failures proved that reusing a pre-crash preflight could create a duplicate transaction for one
plan, and that a crash after durable `COPIED_VERIFIED` could leave an unchanged owned partial after
resume.

A rollback test then exposed that a pre-finalize crash with no owned final target was incorrectly
classified as a rollback failure:

```text
rtk python -m pytest -q tests/test_phase_g_executor.py -k "lock_owner_write_failure or rollback_removes_only"
.F                                                                       [100%]
1 failed, 1 passed, 33 deselected in 0.60s
```

The passing peer test proved malformed lock cleanup after a synthetic owner-write failure. The
failure required identity-bound cleanup of an unchanged owned partial and a terminal `ROLLED_BACK`
state when no final target had been created.

Finally, a doctor traversal test required an explicit unsafe-output diagnosis instead of silently
skipping a reparse-point output root:

```text
rtk python -m pytest -q tests/test_phase_g_executor.py -k "doctor_rejects_reparse_output_root"
F                                                                        [100%]
1 failed, 35 deselected in 0.50s
```

The fixture placed an external `.partial` behind a Windows junction. The failure was the missing
`OUTPUT_ROOT_UNSAFE` diagnosis. The external file remained unchanged and was never classified as
an orphan owned by the plan.

Two MOVE semantics were then specified after a final safety review:

```text
rtk python -m pytest -q tests/test_phase_g_executor.py -k "move_same_hash_unowned or move_target_replacement"
FF                                                                       [100%]
2 failed, 36 deselected in 0.96s
```

The first failure proved that a MOVE incorrectly treated a same-hash pre-existing target as a COPY
`ALREADY_PRESENT`, reported `DONE`, and retained the source. The second proved that a target changed
at `BEFORE_SOURCE_DELETE` was not revalidated, so the source could be deleted after the verified
target identity was lost. The remediation requires truthful pre-existing-target metadata,
identity-bound target revalidation immediately before source deletion, and rollback that restores
the MOVE source without deleting the unowned target.

The failures proved that a durably ROLLED_BACK transaction checked stale approval before returning

## Independent Gate audit RED

After the initial Gate evidence was complete, an independent audit identified four additional P1
contracts. Behavioral tests were added before remediation and run against the accepted Phase G
implementation:

```text
rtk python -m pytest -q tests/test_phase_g_executor.py -k "mutation_time_preflight or move_delete_journal or move_quarantined_source or source_removed_commit_failure or target_changed_during_source_hash or bundle_rollback_preflights"
FFFFFFFFFFFFF                                                            [100%]
13 failed, 84 deselected in 3.63s
```

All thirteen failures reached real filesystem, SQLite, lock, resume, doctor, or rollback behavior:

- six mutation-time preflight cases showed that bundle membership, source, target, capacity,
  writability, and an unrelated global incomplete transaction could change after the caller's
  report without a complete recheck under the acquired mutation lock;
- three missing MOVE deletion fault stages proved there was no durable prepared, quarantined, or
  post-unlink recovery envelope around source removal;
- a quarantined-source doctor/rollback case proved the random deletion quarantine was not journaled
  or recoverable;
- an injected `SOURCE_REMOVED` commit failure proved the source could be absent while the journal
  retained no delete phase or recovery path;
- replacing the target immediately after source hashing proved the earlier target verification was
  not repeated immediately before source removal, so both the source and changed target could be
  deleted;
- modifying one bundle member before rollback proved another member could already be deleted before
  the conflict was discovered.

The fixtures use only temporary generated bytes. The RED run made no implementation change and used
no real library, network, or external API.
